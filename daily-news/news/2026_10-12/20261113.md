#### N-ableの新たなゼロデイ「4EverAble2Shell」、PoC公開から数時間で悪用
https://www.bleepingcomputer.com/news/security/new-n-able-4everable2shell-zero-day-exploited-hours-after-poc-released/

- 要約
    - N-centralの新たな脆弱性「4EverAble2Shell」がPoC公開から数時間で悪用され、少なくとも21台の本番サーバーが侵害されたと研究者が報告した。うち19台は11月10日公開の最新HF2を適用していた。
    - Legacy APIが有効な環境では、未認証の攻撃者がApache AxisのCVE-2026-90436とN-centralの権限昇格を連鎖させ、root権限でコマンドを実行できる。Legacy APIは既定では無効になっている。
    - 攻撃者は外部サーバーからスクリプトを取得し、Moneroマイニング用のXMRigを導入した。利用可能なCPUコアの約半分を使う設定で、マイニングワーカー名にはnc_と侵害サーバーのIPアドレスが使われていた。
    - 同日公開された別のPoC「Agent2Shell」は、N-centralのエージェント機能を通じてWindows端末でSYSTEM権限の実行が可能とされる。記事では、この脆弱性の実環境での悪用は確認されていない。
    - N-ableは追加修正まで一部機能・連携を制限し、Intune連携も予防的に無効化した。ホスティング環境には保護措置を適用済みで、オンプレミス利用者にはLegacy APIの無効化を求めている。

#### Apache HTTP Server、HTTP/2の重大なリモートコード実行脆弱性を修正
https://www.bleepingcomputer.com/news/security/apache-http-server-patches-critical-http-2-remote-code-execution-flaw/

- 要約
    - Apache Software Foundationは、HTTP Serverのmod_http2に存在するCVE-2026-119618を修正した。未認証の攻撃者が、Webサーバープロセスの権限で任意のコードを実行できる恐れがある。
    - 原因はassign_headers()における共有リソースへの並行アクセス時の同期不備で、ヒープメモリの破損につながる。AnthropicのOSS ScannerとGoogle Cloudの脆弱性調査チームが発見した。
    - 影響するのはHTTP Server 2.4.55～2.4.70と、単体版mod_h2 2.0.8～2.0.42。悪用にはHTTP/2が有効である必要があり、既定で無効の構成ではこの条件を満たさない。
    - Wizはクラウド環境の64％に脆弱なリソースがあり、その約半数に公開インスタンスがあると報告した。ただし、この集計はHTTP/2の有効・無効を考慮しておらず、実際に悪用可能な割合を示すものではない。
    - 記事時点でWizは公開された攻撃コードや実際の悪用を確認していない。最新版では、mod_mdのNULLポインター参照(CVE-2026-106023)とmod_vhost_aliasのデータ上書き(CVE-2026-109163)に関する脆弱性も修正された。

- 推奨事項
    - 修正を含む最新版へ更新する。
    - 直ちに更新できない場合は、更新までHTTP/2を無効化する。
- その他
    - 修正公開済みで、記事時点では公開Exploitや実環境での悪用は未確認。
    - 一次ソース:
        - https://httpd.apache.org/security/vulnerabilities_24.html

- ChatGPTの推奨事項

#### Windowsの新たなゼロデイ「SignDrop」、SYSTEM権限への昇格が可能に
https://www.bleepingcomputer.com/news/security/new-windows-signdrop-zero-day-gives-hackers-system-privileges/

- 要約
    - 研究者Abdelhamid Naceri氏は、WindowsでSYSTEM権限へのローカル権限昇格が可能とする「SignDrop」のPoCを公開した。CLFSの保護強化として2025年10月に導入された緩和策の処理を悪用する。
    - 問題はCLFSログの認証ファイル（.cnpf）作成にある。研究者によると、特権プロセスがログを開く際に、元ファイルのアクセス権を引き継いだ認証ファイルをSYSTEM権限で作成させられる。
    - Windows Defenderなどの正規プロセスを介してファイルを作成させるため、自己防御機構を回避し、ウイルス対策やEDRの無効化にも利用できると研究者は主張している。
    - Windows 11 26H2、同Experimental、Windows Server 2025 Experimentalで検証したという。Windows環境の80％が影響するとの数字は研究者の推定で、すべての端末が対象ではない。
    - 研究者はCLFS認証モードが0または1の環境を影響対象としている。記事時点で公式修正はなく、CLFS緩和策の無効化は既存のメモリ破損攻撃への保護を失わせるため、解決策にならないとしている。
- IOCの列挙
    - IOC情報なし
- 推奨事項
    - 研究者は、PoCによる検証またはHKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\CLFS\Authentication\Modeの確認を案内している。値が0または1の場合は脆弱と説明している。
    - CLFS緩和策を無効化せず、Microsoftによる修正を待つ。
- その他
    - PoCは公開済みだが、実際の攻撃での悪用は記事に記載されていない。
    - 一次ソース: https://github.com/MSNightmare/SignDrop
- ChatGPTの推奨事項
    - まずCLFS認証モードを読み取りで確認し、保護機能を維持したまま対象端末を把握してください。

#### 攻撃者がLinuxサーバーにGSocketを設置し、永続的なアクセスを確保
https://www.bleepingcomputer.com/news/security/hackers-plant-gsocket-on-linux-servers-for-persistent-access/

- 要約
    - 複数の攻撃者が正規のオープンソース遠隔アクセスツールGSocketを悪用し、Linuxサーバーへのアクセスを維持している。侵入に使われた脆弱性を修正した後も、設置済みのツールによる接続は継続できる。
    - GSocketは侵害ホストと操作者の双方から中継ネットワークへ外向きに接続し、エンドツーエンドで暗号化された通信を確立する。公開IPや受信用ポート、専用C2サーバーを必要とせず、NAT配下でも接続できる。
    - Microsoft Defender for Endpointの観測では、関連検出が3～8月に356.2％増加した。検出事案の87.1％はWebアプリやホスティング関連で、教育・研究分野が主な標的となっている。
    - 攻撃者はGSocketをカーネルスレッドに偽装し、cron、systemdサービス、シェル起動ファイルを使って永続化していた。一部ではLinuxカーネルのDirty Frag（CVE-2026-43284）によるroot権限取得も試みていた。
    - 外向き通信を使うため、受信側のファイアウォール規則だけでは対処できない。Microsoftは不正なGSocketと関連ファイルの除去、中継網への通信停止確認、送信先制限と永続化設定の監査を推奨している。
- IOCの列挙

- 推奨事項
    - 不正に設置されたGSocketと関連ファイルを削除し、中継ネットワークへの外向き通信が停止したことを確認する。
    - 外向き通信を許可した宛先に制限し、cron、systemdサービス、シェル起動ファイルへの不正な追加を監査する。
    - OSとアプリを最新化し、CVE-2026-43284を含む脆弱性の修正を適用する。
- その他
    - 攻撃者の国籍や所属は記載されていない。

#### eMudhra、秘密鍵の不適切な取り扱いを受け中間CA証明書8件を追加失効
https://www.bleepingcomputer.com/news/security/emudhra-revokes-8-more-ca-certificates-after-private-key-mishap/

- 要約
    - 認証局eMudhraは、秘密鍵の取り扱いに問題があったRSA中間CA証明書8件を11月7日に追加失効させた。既に問題が判明していたECDSA証明書8件と合わせ、影響は計16件となった。
    - 原因は2025年4月に異なるベンダーのHSM間で鍵を移すために使用した独自Pythonスクリプト。バグによってECDSA秘密鍵が1バイトに縮退し、256通りを試すだけで復元できる状態になっていた。
    - RSA鍵の強度は低下していなかったが、HSM内に保護すべき秘密情報をホストのプロセスメモリで扱っていた。証明書運用規程への適合を示せないため、TLS・コード署名用を含む中間CA証明書を失効した。
    - 2025年6月にはCA証明書と一致しない秘密鍵で署名した失効リストを検出していたが、原因を調査せず修正していた。鍵の強度や、HSMで当初生成した鍵との一致を検証していなかったことも判明した。
    - 影響する顧客証明書は交換・移行済みで、秘密鍵の悪用を示す証拠は確認されていない。同社は公開信頼TLS証明書事業から撤退し、残るG1階層での発行を11月16日までに停止する予定。

#### Notion、Fireworks AIの侵害で顧客のAIチャット記録が漏洩したと公表
https://www.bleepingcomputer.com/news/security/notion-says-fireworks-breach-exposed-customer-ai-chat-transcripts/

- 要約
    - Notionは、外部AI基盤事業者Fireworks AIでの侵害により、一部ワークスペースのNotion AIチャット記録が漏洩したと公表した。影響する利用者は全体の1％未満としている。
    - Fireworksは11月2日、合成テストデータのみを含むデータセットの漏洩をNotionへ通知した。Notionは11月3日までに通信を遮断し、同社環境のデータ削除と学習処理の停止を実施した。
    - しかし11月8日、FireworksはNotion利用者を含む顧客データへの不正アクセスを確認した。Notionの分析で、管理者がチームのAI利用状況を把握するInsights機能用のチャット記録が含まれると判明した。
    - 大多数の被害ワークスペースでは記録に利用者名や所属先のラベルがなく、ツール呼び出し結果も含まれていなかった。対象データセットは無効化済みで、Fireworksは契約上データを保持しないと約束していた。
    - 対象ワークスペースの所有者はNotionのSecurity incident reviewから影響データを確認できる。Notionは、該当チャットへ入力したパスワードやAPIキーなどの認証情報を更新するよう推奨している。
